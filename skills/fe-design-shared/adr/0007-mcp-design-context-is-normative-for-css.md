# MCP `get_design_context` output is normative for CSS structure

The Figma MCP `get_design_context` tool returns CSS where every token corresponds 1:1 to a Figma node property — `py-10` ↔ `paddingTop / paddingBottom`, `gap-6` ↔ `itemSpacing`, `rounded-8` ↔ `cornerRadius`, `border-[1.5px]` ↔ `strokeWeight`, and so on. The implementing skill must write the literal equivalent (e.g. `padding: 10px 16px; gap: 6px; border-radius: 8px;`) even when an existing pattern in the project (e.g. `height: 40px` with vertical-center flex) produces the same rendered pixels. Substituting structurally equivalent CSS hides design intent: a future line-height change in Figma adapts automatically with `padding-block`, but a pinned `height` silently clips text. The "looks the same now" check is insufficient — structural fidelity is the contract, and VRT cannot enforce it because pixel comparison sees only the result, not the box-model.

## Consequences

- `fe-design-create` step 4 instructs AI to honor MCP CSS tokens literally. Pre-existing project patterns that diverge (e.g. height-pinned buttons) are noted as refactor candidates in the report, not silently propagated.
- VRT (`fe-design-check`) is necessary but not sufficient — pixels can match while the box-model is semantically wrong. The MCP-literal rule is the structural check; the diff-image read in verify's step 3 is the fallback when generated code has been hand-edited.
- One exception: when a Figma node's `layoutSizingHorizontal` or `layoutSizingVertical` is `HUG`, MCP outputs `w-[N]` / `h-[N]` where `N` is the rendered `text + padding` result, not a design-intended fixed dimension. The skill detects this via REST (`GET /v1/files/<fileId>/nodes?ids=<nodeId>`) and omits the explicit `width` / `height` on the HUG axis, letting content drive. `FIXED` is honored literally; `FILL` becomes `100%` (or `flex: 1` inside an auto-layout parent). The newer `layoutSizing*` fields are preferred over `primaryAxisSizingMode` / `counterAxisSizingMode` because they are axis-stable (horizontal is always width), avoiding per-node reasoning about which axis is "primary".
- Font build matters for the same reason: Figma renders Inter using the rsms.me Variable build; Google Fonts Inter has slightly different metrics. The skill recommends the rsms.me link in `preview-head.html` so VRT noise reflects rendering differences, not font-build divergence.
- Trade-off: components implemented under this rule will diverge from existing project conventions when the author historically chose `height` over `padding-block`. Refactoring the existing components to match is recommended but out of scope for a single implement call — the skill flags the divergence in the report and lets the user decide.
- **Box-model side-effect exception.** Literal MCP CSS occasionally produces unintended box-model behaviour that contradicts Figma's visual intent. The canonical example: MCP outputs `border-bottom: 1px solid <c>` for each list item; in CSS this adds 1px to every item's height, accumulating into visible drift across the list. The skill may substitute equivalent CSS that preserves design intent without the side effect — e.g. `box-shadow: inset 0 -1px 0 <c>` for a divider line. This is not a violation of the rule but a refinement: the rule is "structural fidelity to Figma's intent", not "verbatim copy of MCP tokens". When such substitution happens, the skill must note it in the report so a future reader sees why the CSS diverges from a naïve MCP copy.
